# EasyMCU_ESP32S3 完全解读（总览）

> 面向「懂基础计算机知识、但不懂 C 与硬件」的读者。
> 配套文档：`01-HID手柄伪装`、`02-串口协议`、`03-ECS脚本虚拟机`、`04-编译与烧录`。

---

## 1. 一句话总结

**这个固件让一颗 ESP32-S3 芯片"伪装"成任天堂 Switch Pro 手柄**：PC 通过串口把"按键指令"发给芯片，芯片解析后，通过 USB 接口把指令翻译成 Switch 能识别的"手柄报告"，从而实现对 Switch 的自动化操作（挂机刷游戏等）。它与 EasyCon 软件配套使用。

类比：ESP32-S3 是一个"翻译官"，一头听着 PC 的串口方言（EasyCon 协议），一头对 Switch 说标准普通话（USB HID 手柄协议）。

## 2. 系统全景

```
┌─────────────────────────────────────────────────────────────────┐
│  PC 侧：EasyCon 软件                                              │
│  （实时按键 / 录制 / ECS 脚本编译）                                │
└───────────────┬─────────────────────────────────────────────────┘
                │ COM 口（USB 转串口桥，115200 8N1）
┌───────────────▼─────────────────────────────────────────────────┐
│  EasyMCU 板（ESP32-S3）                                          │
│                                                                │
│   ┌─────────────┐      ┌──────────────────────────────────┐    │
│   │ UART0 (43/44)│────▶│ EasyCon_serial_task() 协议解析   │    │
│   └─────────────┘      └────────┬─────────────────────────┘    │
│                                 │ 实时模式（8字节帧）            │
│                                 │ 脚本模式（ECS 虚拟机）        │
│                                 ▼                             │
│                      switch_hid_report_t（8 字节手柄状态）       │
│                                 ▼                             │
│                      hid_tx_task → TinyUSB → USB-OTG           │
└───────────────┬─────────────────────────────────────────────────┘
                │ "usb" 口（原生 USB，伪装 HID 手柄）
┌───────────────▼─────────────────────────────────────────────────┐
│  Nintendo Switch（把这块板子当作一个合法第三方手柄）              │
└─────────────────────────────────────────────────────────────────┘
```

两种工作模式：

| 模式 | 数据流 | 用途 |
|------|--------|------|
| 实时模式 | PC 每帧发 8 字节按键状态 → 芯片直接改写手柄报告 | 手动控制、录制 |
| 脚本模式 | PC 用 `CMD_FLASH` 烧入字节码 → 芯片上的 VM 自己执行 | 挂机自动化，无需 PC 在线 |

## 3. 硬件原理（零基础版）

### 3.1 ESP32-S3 芯片

乐鑫（Espressif）的 SoC（System on Chip，片上系统），单芯片集成：

| 部件 | 本项目中的作用 |
|------|----------------|
| 双核 Xtensa LX7 CPU @240MHz | 双核并行：Core0 收指令/计时，Core1 发手柄报告/跑脚本 |
| SRAM + 外接 Flash | 运行时内存；固件与数据的持久化存储 |
| 多个 UART 串口控制器 | UART0 接 PC（指令通道）、UART1 接调试日志 |
| **USB-OTG 控制器** | 原生 USB 外设，伪装成 HID 手柄接 Switch |
| GPIO 引脚 | 复用为 UART 引脚、LED（GPIO10）等 |

### 3.2 板子上为什么有两个 USB-C 口

| 口 | 接谁 | 物理通道 | 代码通道 |
|----|------|----------|----------|
| 标 "com" | PC | 板载 USB 转串口桥芯片 → **UART0**（GPIO43 发 / GPIO44 收） | `uart_handler.c` |
| 标 "usb" | Switch | 直连芯片**原生 USB-OTG 引脚** | `hid_device.c`（TinyUSB） |
| （调试） | 可选 | UART1（GPIO17 发 / GPIO18 收），需 CH341A 转接 | `uart1_log_output`（`main.c:77`） |

> 注意：这是 EasyMCU 板子的布局。标准 ESP32-S3-DevKitC-1 **只有一个 USB 口**，其角色需要额外配置（这正是 ns2-studio 风险册 R2 关注的问题）。

### 3.3 为什么 Switch 认这块板子是手柄

USB 设备插上后要向主机"自报家门"（设备描述符）。本固件伪造的身份（`hid_device.c:68-69`）：

```
VID = 0x0F0D   （HORI 公司——任天堂授权第三方外设厂商）
PID = 0x0092   （HORI 某款手柄）
```

+ 一份合法的 HID 报告描述符（按钮/方向/摇杆的格式声明）。

**模拟手柄的根本原理 = 伪造合法 USB 身份 + 报告合法输入格式。**

### 3.4 芯片启动流程（理解烧录的关键）

```
上电 → 芯片内置 ROM bootloader 检查 BOOT 引脚（GPIO0）
  ├─ 为低（按住 BOOT 键时复位）→ 进入下载模式，听电脑烧录指令
  └─ 为高（正常开机）→ 从 Flash 加载 bootloader → 读分区表 → 运行 factory 分区中的应用
```

README 的"按住 BOOT → 按一下 RST → 松开 BOOT"就是强制进入下载模式。所有 ESP32 烧录都是这个原理。

## 5. 核心机制速览

### 5.1 手柄报告（8 字节）

芯片内部维护一个"手柄此刻状态"（`hid_device.h:35`）：

```c
typedef struct {
    uint16_t Button;    // 按键位图：bit0=Y bit1=B bit2=A bit3=X bit4=L bit5=R
                        // bit6=ZL bit7=ZR bit8=- bit9=+ bit10=L摇杆按
                        // bit11=R摇杆按 bit12=HOME bit13=截图
    uint8_t  HAT;       // 方向键：0~7 八方向，8=居中
    uint8_t  LX, LY;    // 左摇杆 X/Y（0~255，128 居中）
    uint8_t  RX, RY;    // 右摇杆 X/Y
    uint8_t  VendorSpec;// 厂商保留
} switch_hid_report_t;  // 共 8 字节（2+1+4+1）
```

任意时刻，这个结构体就是"手柄现在长什么样"。所有功能（实时命令、脚本）最终都是改它，然后 `hid_tx_task` 每 1ms 检查一次把它发出去。

### 5.2 串口字节协议

字节流（115200 8N1），**最高位为 1 的字节 = 帧结束符**。

- **实时控制帧（8 字节）**：按键(14bit)+HAT(4bit)+摇杆(4×7bit) 位打包 → 芯片改写报告 → 回 `0xFF` ACK / `0x00` ERROR
- **命令帧**：`0xA5` 就绪 / `0x81` 探测 / `0x82` 烧写脚本 / `0x83` 开始 / `0x84` 停止 / `0x85` 版本 / `0x86` LED / `0x80` 调试

### 5.3 ECS 脚本虚拟机

EasyCon 的自动化核心：PC 把脚本**编译成 2 字节定长指令流**烧进芯片，芯片上的 VM 逐条解释执行。

- 虚拟内存 512 字节（`mem[]`）：脚本头、摇杆查表、33 个按键计时器、25 个 16 位寄存器、栈、FOR 循环栈
- 指令分两大类：**输入指令**（最高位=1，按键/摇杆 + 时长）与**控制指令**（最高位=0：延时、循环、比较、算术、跳转/调用）
- 时序：`tick_task` 每 1ms 驱动所有倒计时；`script_task` 执行 VM；`WAIT` 通过"让出 CPU，下个 tick 继续"实现

### 5.4 持久化（NVS）

脚本字节、随机种子、LED 设置存进 Flash 的 NVS 分区（断电不丢）。开机时若脚本未标记"禁止自动运行"，自动执行已烧脚本。

## 6. 任务调度（FreeRTOS）

`main.c:143-147` 创建 5 个任务：

| 任务 | 核心 | 优先级 | 栈 | 频率 | 职责 |
|------|------|--------|-----|------|------|
| `tick` | 0 | 6 | 2KB | 1ms 一次 | 驱动全局时间（`EasyCon_tick`） |
| `uart_rx` | 0 | 5 | 4KB | 轮询 | 读 UART0 字节 → 喂协议解析 |
| `cdc_rx` | 0 | 5 | 4KB | 1ms 轮询 | 读 TinyUSB CDC 字节 → 喂协议解析 |
| `hid_tx` | 1 | 4 | 4KB | 1ms 轮询 | 报告可发时发送 HID 报告 |
| `script` | 1 | 3 | 8KB | 连续执行 | ECS 虚拟机主循环 |

设计要点：

- **双核分工**：Core0 = 收指令 + 计时（实时性要求高）；Core1 = 发报告 + 跑脚本（吞吐型）
- **优先级**：tick > 收发 > 报告 > 脚本——时间基准最优先，脚本最不重要（可被抢占）
- **栈大小**：脚本任务 8KB 是因为 VM 有深的调用/循环栈（`CALLSTACK`/`FOR` 数组都在静态区，但编译器临时变量仍占栈）

## 7. 编译（源码 → 固件）

工具链：**ESP-IDF 5.3**（乐鑫官方框架，版本锁定在 `dependencies.lock`）。

```
源码 .c → xtensa 交叉编译器（xtensa-esp32s3-elf-gcc）→ .elf → 拆分为多个 .bin
```

| 配置/文件 | 作用 |
|-----------|------|
| `CMakeLists.txt`（顶层） | `include($ENV{IDF_PATH}/tools/cmake/project.cmake)` 引入 IDF 构建规则 |
| `main/CMakeLists.txt` | `idf_component_register`：声明 5 个源文件 + 依赖（driver/nvs_flash/tinyusb） |
| `main/idf_component.yml` | 组件管理器拉取 `espressif/esp_tinyusb ^2.0.0`（TinyUSB 封装）、IDF ^5.3 |
| `sdkconfig.defaults` | 配置预填：目标芯片 esp32s3、日志走 UART1(GPIO17/18)、TinyUSB 开关、FreeRTOS 1000Hz |
| `partitions*.csv` | Flash 分区表（见下） |

**分区表**（以 `partitions.csv` 为例，8MB Flash 版）：

| 分区 | 偏移 | 大小 | 内容 |
|------|------|------|------|
| nvs | 0x9000 | 24KB | 系统 NVS |
| phy_init | 0xf000 | 4KB | 射频校准参数 |
| factory | 0x10000 | 8MB（16MB 版 6MB） | 应用程序本体 |
| storage | 0x810000 | 7MB（16MB 版 ~10MB） | 脚本数据分区 |

**N8R2 / N8R8 / N16R8 区别**：芯片型号后缀 = Flash 大小 + PSRAM 大小。8MB 板用 `partitions_8mb.csv`（应用区压到 4MB），16MB 板用 `partitions_16mb.csv`。README 只保证 N16R8 可用。

> 本地提示：当前机器**未安装 ESP-IDF**。自己编译需先安装 ESP-IDF 5.3（含 Python、Git、xtensa 工具链）；不想装就直接用 `release_bins/` 现成固件。

## 8. 烧录

| 方式 | 操作 | 适用 |
|------|------|------|
| IDF 标准 | `idf.py -p COMx flash` | 开发者自己编译后烧录 |
| 合并镜像 | ESP Flash Download Tool：选 ESP32-S3 → 选 `release_bins/*.bin` → **地址 0x0** → 选 COM → Start | 用户刷现成固件（README 推荐） |
| 手动 | `esptool.py --chip esp32s3 write_flash 0x0 xxx.bin` | 命令行用户 |

**为什么地址是 0x0**：`pack_bin.ps1` 用 `esptool.py merge_bin` 把 bootloader + 分区表 + 应用合并成**单个完整镜像**（`flash_args` 里记录了每个子文件的地址与 flash 模式/频率），所以整包从 Flash 地址 0 开始放，一个地址搞定。

烧录前提：按住 BOOT → 按 RST → 松开 BOOT，进入下载模式。

## 9. 数据流总回顾

```
[EasyCon 软件] ──COM口──▶ [UART0] ──▶ EasyCon_serial_task() 解析
                                          │
          实时模式(8字节帧)                │ 脚本模式(CMD_FLASH烧入NVS)
                 │                        ▼
                 │                  ECS 虚拟机逐条执行
                 ▼                        │
        set_buttons()/set_left_stick()    │  press_buttons()/release_buttons()
                 └────────────┬───────────┘
                              ▼
                  switch_hid_report_t (8字节手柄状态)
                              ▼
                    hid_tx_task → TinyUSB → "usb"口 → Switch
```

## 10. 与 ns2-studio 的关系

- 这块固件是 **EasyCon 协议的参考实现**（ns2-studio 风险册 R2 的"严格按 EasyMCU 文档"即指此）
- ns2-studio S1 工单（协议包）要对标的 `02-PROTOCOL.md` 就是这套命令：`0xA5/0x81/0x82/0x83/0x85`、8 字节报告帧、7bit 打包
- 本项目的"PC 指令 → Switch"方向，与 S8 工单的"Pro 手柄 → PC"方向正好相反，两者在 InputHub 处汇合
