## 2. 帧格式：最高位定界

字节流**没有固定长度前缀**，靠一个约定：**一帧的最后一个字节，其最高位（bit7）必为 1**。

`EasyCon_serial_task`（`easycon.c:461`）的处理逻辑：

```c
serial_buffer[serial_buffer_length++] = (uint8_t)byte;   // 先累积
if ((byte & 0x80) != 0) {                                 // 帧结束？
    ... 按帧长分发 ...
    serial_buffer_length = 0;                             // 清空，等下一帧
}
```

因为数据字节的最高位被"定界符"占用，所以**每字节实际只有 7 个可用位**——这就是"7-bit 打包"（ns2-studio 协议包 `02-PROTOCOL.md` 的 7bit 打包同源）。防御措施：帧长超过 20 字节（`SERIAL_BUFFER_SIZE`）直接丢弃重来。

## 3. 实时控制帧（8 字节）——手动控制 / 录制

这是 EasyCon 软件控制手柄时高频发送的帧（每秒可达 250 次）。解包代码（`easycon.c:480-485`）：

```c
set_buttons((serial_buffer[0] << 9) | (serial_buffer[1] << 2) | (serial_buffer[2] >> 5));
set_HAT_switch((uint8_t)((serial_buffer[2] << 3) | (serial_buffer[3] >> 4)));
set_left_stick((uint8_t)((serial_buffer[3] << 4) | (serial_buffer[4] >> 3)),
               (uint8_t)((serial_buffer[4] << 5) | (serial_buffer[5] >> 2)));
set_right_stick((uint8_t)((serial_buffer[5] << 6) | (serial_buffer[6] >> 1)),
                (uint8_t)((serial_buffer[6] << 7) | (serial_buffer[7] & 0x7f)));
```

### 3.1 逐位消耗表（7 个字节 × 7 位 + 尾字节 = 56 位）

| 字段 | 字段位 | 来自哪个字节的哪些位 |
|------|--------|----------------------|
| Button | bit0..1 | b2 的 bit5..6 |
| Button | bit2..8 | b1 的 bit0..6 |
| Button | bit9..15 | b0 的 bit0..6 |
| HAT | bit0..2 | b3 的 bit4..6 |
| HAT | bit3..6 | b2 的 bit0..3 |
| LX | bit0..3 | b4 的 bit3..6 |
| LX | bit4..7 | b3 的 bit0..3 |
| LY | bit0..4 | b5 的 bit2..6 |
| LY | bit5..7 | b4 的 bit0..2 |
| RX | bit0..5 | b6 的 bit1..6 |
| RX | bit6..7 | b5 的 bit0..1 |
| RY | bit0..6 | b7 的 bit0..6 |
| RY | bit7 | b6 的 bit0 |
| （未用） | | b2 的 bit4 |

每个中间字节都是"上一字段的尾巴 + 下一字段的开头"（移位拼接），这就是经典的**跨字节位打包**。

### 3.2 尾字节与帧结束符合一

第 8 个字节（b7）的低 7 位是 RY，而它的 **bit7 就是帧结束符**（`0x80`），解包时用 `& 0x7f` 剥掉。所以：

```
8 字节帧 = [b0][b1][b2][b3][b4][b5][b6][RY | 0x80]
```

> 注意：PC 端必须保证**只有最后一字节** bit7=1，否则固件提前判帧结束、解包错乱。

### 3.3 完整示例

"按住 A + B，方向居中，四摇杆居中"：

- Button = A(bit2) | B(bit1) = `0x0006`
- b0 = (Button >> 9) & 0x7F = 0
- b1 = (Button >> 2) & 0x7F = 1
- b2 = (Button & 0x3) << 5 | (HAT >> 3) = 0x00 | 1 = `0x01`
- b3 = (LX >> 4) | (HAT & 0x7) << 4 = 8 | 0 = `0x08`
- b4 = (LX & 0xF) | (LY >> 5) << 3 = 8 | 0 = `0x08`
- b5 = (LY >> 2) | (RX >> 6) << 2 = 0
- b6 = (RX >> 1) | (RY >> 7) << 1 = 0
- b7 = (RY & 0x7F) | 0x80 = `0x80`

帧：`00 01 01 08 08 00 00 80`

### 3.4 固件应答

解包成功后（`easycon.c:487-492`）：

| 条件 | 应答 |
|------|------|
| 脚本正在运行 | `0xFE`（BUSY）——实时命令被拒绝，防止与脚本打架 |
| 手柄已就绪（`hid_device_is_ready`） | 发送报告 + `0xFF`（ACK） |
| 手柄未就绪 | `0x00`（ERROR） |

## 4. 命令帧（1 字节帧）——控制类

帧长为 1 且固件处于"就绪"状态时，按字节值分发（`easycon.c:497-552`）：

| 命令 | 值 | 帧长 | 固件动作 | 应答 |
|------|-----|------|----------|------|
| `CMD_DEBUG` | 0x80 | 1 | 返回 14 字节调试信息（见下） | 数据帧 |
| `CMD_HELLO` | 0x81 | 1 | 探测设备在线 | `0x80` |
| `CMD_FLASH` | 0x82 | **5** | 进入烧写模式，解析地址/长度 | `0x81`（FLASHSTART） |
| `CMD_SCRIPTSTART` | 0x83 | 1 | 启动 ECS 脚本 | `0x83` |
| `CMD_SCRIPTSTOP` | 0x84 | 1 | 停止脚本 + 报告复位中立 | `0x83` |
| `CMD_VERSION` | 0x85 | 1 | 返回固件版本 | `0x46`（VERSION 宏） |
| `CMD_LED` | 0x86 | 1 | 翻转 LED 标志 bit3 并持久化 | `_ledflag` |
| `CMD_READY` | 0xA5 | 1 | 恢复"就绪"状态（见第 6 节） | — |

未知命令 → `0x00`（ERROR）。

**DEBUG 应答格式**（14 字节，全部小端）：

| 字节 | 内容 |
|------|------|
| 0..3 | 当前 FOR 循环迭代值（`FOR_I(_forstackindex-1)`） |
| 4..7 | 脚本累计运行时间 `timer_elapsed` |
| 8..9 | 当前脚本地址 `script_addr` |
| 10..11 | 报告发送计数（当前固件恒为 0） |
| 12..13 | 报告失败计数（当前固件恒为 0） |

> EasyCon 软件的"调试面板/脚本单步"功能就是靠这帧。

## 5. 烧写脚本流程（`CMD_FLASH`）

脚本不是一次性传完，而是**分块**：

```
PC:  0x82  addr_lo(7bit)  addr_hi(7bit)  len_lo(7bit)  len_hi(7bit)      ← 5 字节帧
FW:  应答 0x81（FLASHSTART），停止当前脚本，准备接收 len 字节
PC:  连续发送 len 个数据字节（每块 ≤ 19 字节，受 SERIAL_BUFFER_SIZE 限制）
FW:  收到 len 字节后：逐字节写入 NVS（key = "b<addr+i>"），应答 0x82（FLASHEND）
重复直到整段脚本写完
```

- 地址/长度均为 **14 位**（`addr = b0 | b1<<7`，`len = b2 | b3<<7`）
- 数据字节**允许** bit7=1（烧写模式在帧结束判断之前拦截，见 `easycon.c:463`）
- 所有块写完、帧结束时触发 `EasyCon_write_end(0)` 提交 NVS（`easycon.c:553-555` 的"非命令帧结尾提交"逻辑）

## 6. 就绪握手（READY 机制）

`serial_command_ready` 初始为 `true`，收到一个完整 8 字节帧后变 `false`（`easycon.c:494`）。此后：

- 只有 1 字节的 `CMD_READY`(0xA5) 能把状态拉回 `true`（`easycon.c:474` 和 `case CMD_READY`）
- 未就绪时收到任何其他字节 → 固件回显**当前累积长度**（`easycon.c:557`，一种极简的诊断信号）

这是 EasyCon 软件连接时的"探测/复位协议"：`HELLO` 问在线 → `READY` 建立会话 → 才开始发命令。防呆点：脚本运行期间 8 字节帧会被 `REPLY_BUSY` 拒绝，而命令类（如 SCRIPTSTOP）仍然有效——保证永远有逃生通道。

## 7. 报告回显节流（`_report_echo` / `echo_ms`）

固件每次把 HID 报告发给 Switch 后，都会把同一状态 echo 回 PC（`EasyCon_report_send_callback` → `_report_echo` 倒计时），让 PC 端 UI 能显示"当前手柄状态"。为了防止高频刷屏：

```c
// easycon.c:114
void EasyCon_report_send_callback(void) {
    if (!_script_running || _report_echo > 0 || wait_ms < 2) {
        _report_echo = Max(0, _report_echo - 1);
    }
    echo_ms = ECHO_INTERVAL;   // = 2ms 的发送闸门
}
```

- `echo_ms`：HID 发送闸门（`EasyCon_need_send_report()` 返回 `echo_ms == 0`），每次发送后重置为 2ms
- `_report_echo`：报告回显上限（`ECHO_TIMES = 2`），即一串连续报告中最多回显 2 次，避免脚本快速连按把串口刷爆

## 9. 关键认知总结

1. **一帧一字节定界**：bit7=1 的字节是帧结束符，每字节实际只有 7 位数据——所有字段都按 7 位粒度跨字节打包。
2. **两种帧互不冲突**：8 字节实时帧优先于命令帧判断（`easycon.c:476` 先判长度）。
3. **写保护**：脚本运行时实时帧被 BUSY 拒绝；烧写会先 `SCRIPTSTOP`。
4. **收尾提交**：NVS 写入不是逐字节提交，而是帧尾统一 `nvs_commit`（性能考虑）。
5. **与 ns2-studio 的关系**：这套命令集就是 S1 工单要对标的 EasyCon 协议；S0b 固件需要实现同样的字节语义。
